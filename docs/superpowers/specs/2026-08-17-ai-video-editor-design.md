# AI Video Editor — design

Cuts a recorded take down to what you meant to say, keeping a camera track and a
screen-feed track in sync, then offers visual effects for the screen feed.

## Why

A talking-head recording with a screen capture has two problems the existing
Shorts Generator does not solve: long pauses, and the same sentence read three
times because the first two takes were wrong. Both are fixable from the
transcript. The two files must be cut identically or they drift apart.

## Decisions

| Question | Decision |
|---|---|
| Track sync | Both recordings start together, so timestamp 0 is the same moment. Identical cut ranges are the entire sync mechanism. No alignment pass. |
| Duplicate detection | One LLM call over numbered transcript segments. Catches stumbles and false starts that string similarity misses. |
| Review | Transcript editor: the transcript IS the timeline. Struck text = removed. |
| Output | One edited file per source, still in sync. No compositing. |
| Dead air | Gap between words > 0.7s, keeping 0.15s padding. Both adjustable. |

## Model

One record per edit, `editor/<id>.json` in the active project's vault:

```
{ id, title, status, camera_path, screen_path, transcript[], removals[], error }
```

A **removal** is `{start, end, reason}` where reason is `silence | duplicate |
manual`. Removals — not keep-ranges — are the stored unit, so an AI proposal and
a hand edit are the same kind of object and "restore this" is deleting one.

`status`: `pending` → `analysing` → `review` → `rendering` → `done` | `failed`.

## Components

Each does one thing and is testable alone.

- **`DeadAirDetector`** — pure. Word timestamps → silence removals. No AI.
- **`DuplicateTakeDetector`** — one LLM call. Segments → groups of retakes;
  keeps the last of each group, removes the earlier ones.
- **`CutPlan`** — pure. Removals + duration → merged, ordered keep-ranges.
  Handles overlapping and touching removals.
- **`MultiCutEngine`** — one ffmpeg pass per source using `select`/`aselect`
  with `between(t,…)` plus `setpts`/`asetpts` to close the gaps. Not N cuts and
  a concat: one re-encode, frame-accurate, no temp files. Exposes
  `buildCutArgs()` so the filter string is testable without running ffmpeg,
  matching `FfmpegVideoCompositor::buildOverlayArgs()`.
- **`EditorStore`** — vault-backed, modelled on `VfxStore`.
- **`SfxPlanner`** (step 2) — LLM proposes `{at, brief}` moments over the
  approved transcript.

## Flow

1. Upload camera + screen. `AnalyseEditJob`: transcribe the **camera** audio
   once (`LocalVideoEngine::transcribe`), run both detectors, store removals,
   set `review`.
2. You review in the transcript editor and approve.
3. `RenderEditJob`: `CutPlan` → keep-ranges → `MultiCutEngine` over both
   sources with the SAME ranges → two files, `done`.
4. Step 2: `SfxPlanner` proposes moments; each is generated by the existing
   `EffectGenerator` with `transparent: true` (alpha ProRes) and composited onto
   the screen feed with `FfmpegVideoCompositor::overlay()`.

## Reused, not rebuilt

`LocalVideoEngine::transcribe/probe`, `FfmpegVideoCompositor::overlay`,
`EffectGenerator` + its design-system guard, the alpha render path from VFX Lab,
`LlmClient` and the `RunsInProject` job trait.

## Testing

Pure functions (dead air, cut plan) get table tests. The ffmpeg filter is
asserted through `buildCutArgs()`. The LLM pass uses a stubbed `LlmClient`. The
render itself is exercised through the fake engine, as the clips tests do.

## Known limits

- Re-encoding two long files takes minutes — rendering is a queued job.
- Whisper on a long recording is slow, and cannot be exercised locally while
  `CLIPS_DRIVER=fake`.
- Step 2 places effects on the screen feed only, at whole-second offsets.
